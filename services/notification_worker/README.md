# Notification Worker

Сервис приёма и отправки email-уведомлений онлайн-кинотеатра. Принимает задания
из Kafka, сохраняет их в собственной PostgreSQL, получает email и ФИО из Auth,
формирует письмо и отправляет его через SMTP. Повторы и результаты сохраняются
в БД и переживают перезапуск процессов.

[Notification Service](../notification_service/README.md) создаёт задания и
предоставляет API управления. У worker нет пользовательского REST API.

## Зависимости

Воркера запускает общий Docker Compose монорепозитория. Он использует собственную
базу `deliveries` в PostgreSQL, топики Kafka, внутренний API Auth и SMTP-сервер.
В локальном окружении SMTP предоставляет Mailpit; письма доступны на
<http://localhost:8025>.

## Возможности

- проверка версионированного контракта входящего задания;
- дедупликация по delivery_id и обнаружение разных заданий с одинаковым ID;
- подтверждение Kafka offset только после сохранения задания;
- публикация некорректных сообщений в DLQ до подтверждения offset;
- получение адресата из Auth непосредственно перед отправкой;
- текстовые и HTML-письма с ограниченным синтаксисом шаблонов;
- безопасная подстановка переменных и HTML-экранирование;
- несколько отправителей с PostgreSQL SKIP LOCKED и арендой задания;
- сохраняемые повторы с экспоненциальной задержкой и jitter;
- outbox результатов и отдельные события окончательной ошибки;
- служебные health/readiness, метрики, JSON-логи и трассировка.

## Архитектура

| Каталог | Ответственность |
|---|---|
| `src/core` | Настройки, PostgreSQL, жизненный цикл и наблюдаемость |
| `src/models` | Версионированный контракт заданий |
| `src/repositories/interfaces` | Интерфейс приёма заданий |
| `src/repositories/postgres` | Дедупликация, захват задания и сохранение результата |
| `src/services` | Приём, взаимодействие с Auth, шаблонизация и SMTP |
| `src/messaging` | Kafka consumer, sender и relay результатов |
| `alembic` | Миграции собственной базы данных |

Образ запускается тремя независимыми процессами:

| Контейнер | Команда | Назначение |
|---|---|---|
| `notification-worker` | `python -m messaging.consumer` | Приём Kafka и сохранение заданий |
| `notification-sender` | `python -m messaging.sender` | Получение адресата и отправка письма |
| `notification-results-outbox` | `python -m messaging.relay` | Публикация результатов из outbox |

SMTP не выполняется внутри Kafka consumer. Поэтому медленная почта не удерживает
подтверждение уже сохранённого входящего задания. Каждый процесс запускается
в отдельном контейнере с собственным служебным портом 8000.

## PostgreSQL

Worker использует базу `deliveries` и пользователя `delivery`. База
`notifications` принадлежит Notification API; worker не записывает в неё напрямую.

| Таблица | Назначение |
|---|---|
| `delivery_jobs` | Исходное задание, состояние, попытка, срок аренды и время повтора |
| `smtp_state` | Общая пауза SMTP и аренда проверки восстановления |
| `outbox` | Результаты и окончательные ошибки для последующей публикации в Kafka |

| Статус | Значение |
|---|---|
| `pending` | Задание сохранено и ожидает отправителя |
| `processing` | Попытка захвачена, действует lease и claim_token |
| `retry` | Временная ошибка, следующий запуск по next_attempt_at |
| `sent` | SMTP-сервер принял письмо |
| `failed` | Постоянная ошибка или исчерпан бюджет попыток |

Номер попытки увеличивается до обращения к сети. При ошибке SMTP-авторизации
номер возвращается: исправное задание не расходует бюджет из-за общей настройки. Повторный захват после падения
тоже расходует бюджет. После исчерпания бюджета восстановительный захват может
увеличить счётчик ещё раз, но SMTP при этом уже не вызывается.

## Kafka и контракт

Входящий топик — `notification-delivery-v1`, группа — `notification-worker-v1`.
Consumer использует явные синхронные подтверждения offsets. При сбое БД или
неудачной отправке в DLQ неподтверждённое сообщение будет прочитано повторно.

Обязательные идентификаторы задания: event_id, delivery_id, notification_id,
user_id. Также передаются schema_version=1, channel=email, снимок template,
trace_context и необязательный context. Копия модели контракта в Notification API
должна оставаться совместимой с копией worker.

Некорректный контракт и коллизия delivery_id попадают в
`notification-delivery-v1-dlq`. Конверт содержит безопасное имя причины,
координаты сообщения и исходные байты в base64. Доступ к DLQ следует ограничивать:
исходное некорректное сообщение может содержать произвольные данные отправителя.

Исходы попыток публикуются в `notification-results-v1`. Для failed дополнительно
публикуется событие в `notification-failed-v1` со снимком исходного задания.
Повтор failed-задания с прежним delivery_id не инициирует повторную отправку;
для осознанной повторной доставки создайте новую заявку через Notification API.

## Конфигурация

Настройки читаются из окружения и `.env`; пример локальной конфигурации находится
в `.env.example`. Если `.env` отсутствует, скопируйте пример перед запуском.
Пустые `SMTP_USERNAME` и `SMTP_PASSWORD` корректны для Mailpit.

| Переменная | Назначение / значение |
|---|---|
| `DATABASE_URL` | `postgresql+asyncpg://delivery:delivery@notification-postgres/deliveries` |
| `KAFKA_BOOTSTRAP_SERVERS` | Внутренние адреса трёх брокеров |
| `JOBS_TOPIC` | `notification-delivery-v1` |
| `CONSUMER_GROUP` | `notification-worker-v1` |
| `DLQ_TOPIC` | `notification-delivery-v1-dlq` |
| `RESULTS_TOPIC` | `notification-results-v1` |
| `FAILED_TOPIC` | `notification-failed-v1` |
| `AUTH_BASE_URL` | `http://auth-service:8000/api/v1/` |
| `INTERNAL_TOKEN` | `notification-worker-local-test` |
| `SMTP_HOST`, `SMTP_PORT` | `mailpit`, `1025` |
| `SMTP_MODE` | `plain`, `starttls` или `tls`; локально plain |
| `SMTP_SENDER` | `cinema@example.com` |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | SMTP-авторизация; локально пустые |
| `SMTP_TIMEOUT` | 20 секунд, допустимо от 1 до 30 |
| `MAX_ATTEMPTS` | 5; допустимо от 1 до 20 |
| `RETRY_BASE_SECONDS` | Базовая задержка 30 секунд |
| `RETRY_MAX_SECONDS` | Верхняя граница задержки 3600 секунд |
| `LEASE_SECONDS` | 180 секунд; минимум 120 |
| `POLL_SECONDS` | Пауза пустого цикла, по умолчанию 1 секунда |
| `KAFKA_TIMEOUT_SECONDS` | По умолчанию 20 секунд |
| `HEALTH_STALE_SECONDS` | По умолчанию 90 секунд |
| `SENTRY_DSN` | Пустое значение отключает Sentry |
| `OTEL_ENDPOINT` | `http://jaeger:4317`; пустое значение отключает экспорт |
| `SERVICE_NAME` | Имя процесса для OpenTelemetry |

INTERNAL_TOKEN должен совпадать с NOTIFICATION_WORKER_TOKEN в Auth.
Sender вызывает `GET /api/v1/internal/notifications/users/{user_id}` с
`X-Service-Token`. Этот метод должен возвращать id, email, first_name, last_name
и is_active. UUID и активность проверяются перед SMTP. Неактивный или отсутствующий
получатель приводит к failed; недоступность Auth — к сохраняемому повтору.

Для внешнего SMTP задайте адрес, порт, режим шифрования и необходимые учётные
данные. После изменения env_file пересоздайте sender; простой restart не изменяет
переменные окружения уже созданного контейнера.

## Запуск и миграции

Из корня монорепозитория:

```bash
docker compose run --rm delivery-migrate
docker compose up -d --build auth-service mailpit \
  notification-worker notification-sender notification-results-outbox
```

Kafka-топики, база deliveries, Auth и Mailpit должны быть доступны.
Для полного сценария также запускаются Notification API и его фоновые процессы.
Миграции worker выполняются отдельной командой, не каждым consumer/sender.
Ревизия 0002 сохраняет историю и запрещает destructive downgrade.

Для локальной установки, из каталога worker:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
export PYTHONPATH="$PWD/src"
alembic upgrade head
python -m messaging.consumer
```

Адреса зависимостей в .env должны быть доступны с хоста. При таком способе
запуска consumer остаётся единственным фоновым процессом на этом хосте/порту:
consumer, sender и relay используют общий служебный порт 8000 и имя heartbeat.
Для одновременной работы используйте отдельные контейнеры.

## Шаблоны и персональные данные

Поддерживаются только подстановки `{{ variable }}`. Worker загружает email и ФИО
из Auth в память на время отправки. Эти поля не добавляются в сохранённый payload
или результаты доставки. first_name/last_name из Auth имеют приоритет; API
запрещает одноимённые ключи context. Для HTML значения переменных экранируются.

Отсутствующая переменная, недопустимый шаблон или перенос строки в теме дают
постоянную ошибку. Message-ID строится из delivery_id и остаётся одинаковым
между попытками. Текст SMTP-ответа, email и письмо не записываются в прикладные
сообщения об ошибках; сохраняется безопасный error_code.

## Гарантии доставки

Задание сохраняется до подтверждения Kafka. Уникальный delivery_id предотвращает
повторное создание записи. Несовпадающий payload с тем же ID считается коллизией.

Sender захватывает запись через FOR UPDATE SKIP LOCKED и фиксирует срок аренды
и claim_token до сетевых действий. Фиксация результата проверяет claim_token:
запоздавший процесс не перезапишет результат нового владельца. Результат попытки
и outbox сохраняются одной транзакцией. Затем relay публикует событие в Kafka
и отмечает запись опубликованной только после подтверждения брокера.

Общий дедлайн штатной попытки — 60 секунд, меньше минимального lease.
После аварийной остановки processing-задание доступно по истечении lease.
Это не гарантирует единственную отправку письма: SMTP может принять его до
таймаута или падения процесса. Повтор SMTP при неоднозначном результате допустим.
Стабильный Message-ID помогает сопоставлению, но не обязывает почтовый сервер
устранять дубли. Статус sent означает принятие SMTP, а не прочтение письма.

## Служебные endpoints и логи

У каждого процесса внутри его контейнера доступны:

| Endpoint | Назначение |
|---|---|
| `/health` | HTTP-процесс работает |
| `/ready` | Последняя успешная итерация достаточно свежая |
| `/metrics` | Метрики Prometheus |

Readiness sender без заданий не проверяет SMTP-авторизацию: полноценная проверка
требует отправки задания. Healthcheck Docker запускает `python -m core.health`.
Unhealthy не означает автоматический перезапуск живого процесса.

При запуске общего стека Filebeat передаёт логи в ELK. Локально:

```bash
docker compose logs --tail=100 notification-worker notification-sender \
  notification-results-outbox
```

При включённом OTLP SMTP-span продолжает traceparent задания.
SENTRY_DSN включает отправку статических сообщений об ошибках без данных письма.
SIGTERM позволяет завершить текущую операцию и закрыть соединения.
В Compose для фоновых процессов задан `stop_grace_period: 90s`.

## Ошибки SMTP-авторизации и диагностика

`SMTPAuthenticationError` обрабатывается отдельно от постоянных ошибок письма.
Sender сохраняет общую паузу в `smtp_state` и возвращает своё задание в `retry`
с `smtp_authentication_failed`, освобождая аренду и возвращая номер попытки.
Новые задания остаются в очереди; уже захваченные другими процессами могут
завершить текущую попытку. Пауза переживает перезапуск всех sender-процессов.

Во время паузы `/ready` возвращает 503. Один sender проверяет подключение и
авторизацию без отправки письма: первая проверка через 30 секунд, повторная после
ошибки также через 30 секунд. Аренда проверки — 90 секунд, сетевой дедлайн —
60 секунд. При падении проверяющего процесса другой sender продолжит после аренды.
Успех снимает общую паузу. Все sender должны использовать одинаковую конфигурацию.

После исправления пароля в `.env` пересоздайте sender, чтобы он получил новые
переменные окружения:

```bash
docker compose up -d --force-recreate notification-sender
```

Ошибка авторизации не публикуется как результат попытки: Notification API
сохраняет предыдущий статус до следующего результата отправки. Причина и пауза
доступны в БД воркера, логах, readiness и метриках. Уже завершённые `failed`
задания старой версии автоматически не переоткрываются: старый `smtp_rejected`
не позволяет отличить ошибку пароля от постоянного отказа SMTP.

`auth_unavailable`, `invalid_auth_response` и `smtp_temporary_failure` сохраняются
в результатах без замены общим кодом. Неожиданные исключения получают
`transient_delivery_failure`. Счётчик `notification_delivery_errors_total`
содержит метку `error_code`; ERROR-логи передаются в Sentry при заданном DSN.
Используется фиксированный набор кодов: текст исключения, адрес и письмо не
попадают в журнал или метки метрик. При временной ошибке sender становится
не готов; пустой цикл не восстанавливает readiness. Готовность возвращается
после успешной отправки либо восстановления SMTP-проверкой.

Шаблонизатор ограничивает результат 200 000 символами, включая расширение
HTML-сущностей. Размер проверяется до экранирования и добавления фрагмента,
поэтому слишком большой результат не создаётся целиком в памяти.
## Имена из профилей

Получатель (email и активность аккаунта) проверяется через Auth.
Имя и фамилия загружаются через внутренний Profile API с `PROFILE_TOKEN`.
При 404 письмо отправляется без имени; при отказе или недоступности сервиса
сохраняется повтор доставки. `PROFILE_TOKEN` должен совпадать с
`NOTIFICATION_TOKEN` в Profile; готовые `.env` уже согласованы.
[Описание](../profile_service/README.md).
