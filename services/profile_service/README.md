# Profile Service

Профили пользователей с отдельным PostgreSQL-хранилищем. Auth отвечает за
учётную запись и права, Profile — за ФИО и телефон, UGC — за закладки,
оценки и рецензии. Идентификатор пользователя общий: UUID из Auth.

## Запуск

```bash
docker compose build
docker compose up -d
```

Для последующих запусков достаточно `docker compose up -d`.
Profile запускается существующим Compose. Миграции выполняются внутри
его контейнера при старте. Готовые `.env` и `.env.example` включены только
для Profile и затронутых интеграций: Auth, Admin и Notification Worker.
Существующие настройки остальных сервисов не меняются.

Параметры для входа администратора находятся в `services/auth_service/.env`:
`SUPERUSER_LOGIN` и `SUPERUSER_PASSWORD`. Если администратора ещё нет,
после готовности Auth выполните прежнюю команду:

```bash
docker compose exec auth-service python -m src.commands.create_superuser
```

Новые параметры окружения:

| Сервис | Параметры |
| --- | --- |
| Auth | `PROFILE_NAMES_EXTERNAL`, `PROFILE_MIGRATION_TOKEN` |
| Admin | `PROFILE_SERVICE_BASE_URL`, `ADMIN_TOKEN_KEY` |
| Notification Worker | `PROFILE_BASE_URL`, `PROFILE_TOKEN` |
| Profile | собственная БД, `ENCRYPTION_KEYS`, `PHONE_INDEX_KEY`, `NOTIFICATION_TOKEN`, `MIGRATION_TOKEN` |

Внутренние токены и ключи уже согласованы. При переносе на существующее
окружение сохраняйте его пароли БД и ключи шифрования. `.env.example`
служат шаблонами; копировать их поверх подготовленных `.env` не нужно.

Swagger: <http://127.0.0.1:8000/profiles/docs>.
Health: `/profiles/health`; readiness с проверкой таблицы БД:
`/profiles/ready`. Миграции Alembic выполняются при старте контейнера.

## API

Все методы `/api/v1/profiles` требуют Bearer access-токен Auth.

| Метод | Путь | Доступ |
| --- | --- | --- |
| POST | `/api/v1/profiles/me` | Создать собственный профиль |
| GET | `/api/v1/profiles/me` | Прочитать собственный профиль |
| PATCH | `/api/v1/profiles/me` | Изменить собственный профиль |
| DELETE | `/api/v1/profiles/me` | Удалить собственный профиль |
| GET | `/api/v1/profiles/?limit=50&after=<UUID>` | `profiles:read` или суперпользователь |
| GET | `/api/v1/profiles/<user_id>` | `profiles:read` или суперпользователь |

Пример POST:

```json
{
  "first_name": "Анна",
  "last_name": "Иванова",
  "middle_name": "Петровна",
  "phone": "+12025550123",
  "marketing_consent": false
}
```

Имя и фамилия обязательны для нового профиля. Отчество и телефон можно
не заполнять. PATCH меняет только переданные поля; `null` очищает телефон
или отчество. Имя, фамилия и согласие на маркетинг не принимают `null`.
Телефон задаётся с международным префиксом `+`, нормализуется к E.164;
добавочные номера отклоняются. Уникальность обеспечивается БД, в том числе
при одновременных запросах. Ответы: 401 без действующего токена, 403 без
права, 404 при отсутствии профиля, 409 при конфликте, 422 при неверном теле.

`user_id`, даты и `phone_verified_at` недоступны для записи клиентом.
Телефон пока не подтверждается: SMS/2FA находятся за границами этих шести
требований. Неподтверждённый номер нельзя использовать как фактор входа или
как доказательство личности. Смена номера сбрасывает его подтверждение.

DELETE физически удаляет зашифрованные персональные данные и освобождает
номер. Аккаунт Auth, закладки, оценки и рецензии остаются: их жизненный цикл
отдельный. Аудит и UUID-маркер импорта сохраняются без ФИО и телефона.
Удаление резервных копий требует отдельной политики хранения.

## Профиль и UGC

Пункты задания про фильмы используют существующий UGC API:

| Действие | API |
| --- | --- |
| Добавить/убрать фильм | PUT/DELETE `/api/v1/bookmarks/<film_id>` |
| Мои фильмы | GET `/api/v1/bookmarks/` |
| Поставить/изменить оценку 0–10 | PUT `/api/v1/ratings/<film_id>` |
| Мои оценки | GET `/api/v1/ratings/me?page_size=50&after=<film_id>` |
| Создать отзыв | POST `/api/v1/reviews/films/<film_id>` |
| Изменить/удалить свой отзыв | PATCH/DELETE `/api/v1/reviews/<review_id>` |
| Мои отзывы | GET `/api/v1/reviews/me?page_size=50&after=<review_id>` |
| Отзывы о фильме | GET `/api/v1/reviews/films/<film_id>` |
| Пользовательский рейтинг фильма | GET `/api/v1/ratings/<film_id>/stats` |

Списки `me` возвращают `items` и `next_cursor`; продолжение передаётся
в `after`. Общий рейтинг пользователей отдельный от `imdb_rating` Content.
В ответах UGC остаются UUID/логин автора; ФИО и телефон туда не передаются.

## Админка и права

Раздел: <http://127.0.0.1:8000/admin/profiles/>. Есть список с пагинацией,
переход по UUID и карточка только для чтения. Телефон в списке маскируется.

Миграция Auth создаёт permission `profiles:read` и роль `profile_reader`
без автоматического назначения пользователям. Суперпользователь получает
UUID роли через `GET /api/v1/roles/`, затем назначает её сотруднику:

```text
POST /api/v1/users/<user_id>/roles/<role_id>
Authorization: Bearer <superuser_access_token>
```

Сотрудник входит в Django Admin с логином и паролем Auth. Статус
`is_superuser` ему не выдаётся. Доступ к контентной админке остаётся
у суперпользователей. Auth проверяется на каждом защищённом запросе,
Profile повторно проверяет permission при обращении к своему API.

Access/refresh-токены зашифрованы отдельным `ADMIN_TOKEN_KEY` в служебной
SQLite админки. В браузере находится только идентификатор Django-сессии.
Refresh сериализован блокировкой записи; конкурентный запрос во время
обновления может получить 503 и должен быть повторён. Выход отзывает
refresh-сессию Auth. После обновления старые Django-сессии требуют входа.

Очистка истёкших серверных сессий:

```bash
docker compose exec admin-service python manage.py cleanup_auth_sessions
```

Для HTTPS включите `SESSION_COOKIE_SECURE=true` в `.env` админки.

## Перенос существующих имён

1. Сделать резервные копии Auth, Profile и их ключей.
2. В Auth включить `PROFILE_NAMES_EXTERNAL=true` (пример и новые `.env`
   уже используют это значение), пересоздать Auth и Notification Sender.
3. Скопировать имена. Команда обращается к внутреннему API Auth и не
   подключается напрямую к чужой БД:

```bash
docker compose exec profile-service python -m src.commands.import_auth_profiles
```

4. Проверить профили. После проверки выполнить повторно с очисткой старых
   полей в Auth:

```bash
docker compose exec profile-service python -m src.commands.import_auth_profiles --clear-source
```

Очистка каждой партии происходит после фиксации всех её целевых записей.
Повторный импорт не перезаписывает актуальный профиль и не восстанавливает
удалённый. Очистка в Auth сравнивает исходные имена со снимком и сбрасывает
соответствующий кеш. Телефоны старых пользователей остаются незаполненными.

При включённом флаге Auth перестаёт сохранять новые имена (включая OAuth),
возвращает `null` в старых полях ответа и отклоняет старый PATCH профиля с
409 `use_profiles_api`. Регистрация с ФИО отклоняется: после регистрации
нужно создать профиль отдельно. Старые колонки остаются для безопасного
переноса и совместимости; после `--clear-source` имена в них очищены.
Зависимости Auth от работающего Profile при проверке токенов нет.

Worker получает email из Auth, имя и фамилию — из защищённого внутреннего
метода Profile. При отсутствии профиля письмо отправляется без имени;
при сбое Profile используется существующий механизм повторов. Это также
позволяет отправить приветственное письмо до создания профиля.

Внутренние методы `/api/v1/internal/` закрыты Nginx и дополнительно
защищены разными токенами для Worker и миграции. Worker не получает телефон.
После переноса можно отключить внутренний API миграции, очистив
`PROFILE_MIGRATION_TOKEN` в Auth и пересоздав Auth.

## Защита и ключи

ФИО и телефон хранятся одним аутентифицированным зашифрованным объектом
Fernet, привязанным к UUID пользователя. Для сравнения телефонов хранится
HMAC-SHA256 с отдельным ключом и уникальным индексом. Ключи не хранятся в
БД; `.env` исключены из Git и Docker-образов. Подготовленные `.env` нужны
для локальной разработки; в развёрнутом окружении секреты должны поступать
через защищённую конфигурацию окружения/секрет-хранилище.

Profile не кеширует персональные ответы и выставляет `Cache-Control:
no-store`. Валидация не возвращает введённые данные, Sentry очищает
контекст запроса и локальные переменные. Аудит содержит только UUID
действующего лица/профиля, действие, время и request ID.

Для ротации шифрования задайте `ENCRYPTION_KEYS=new_key,old_key`,
пересоздайте Profile и выполните:

```bash
docker compose exec profile-service python -m src.commands.rotate_encryption
```

После успешной ротации можно оставить новый ключ. Старый ключ нужен
для старых резервных копий. `PHONE_INDEX_KEY` этой командой не меняется:
его замена требует отдельного пересчёта индекса под контролем записи.

## Проверки

Тесты Profile используют настоящий ASGI API, SQLAlchemy-репозиторий и
первую миграцию. Только Auth заменён HTTP-транспортом с тестовыми ответами.
Без `TEST_DATABASE_URL` используется временный SQLite; Compose запускает
тот же набор на PostgreSQL 16:

```bash
cd services/profile_service/tests/functional
cp .env.example .env
docker compose -p movies-profile-tests up --build --abort-on-container-exit --exit-code-from tests tests
docker compose -p movies-profile-tests down -v --remove-orphans
```

Локально из `services/profile_service`:

```bash
python -m pip install -r requirements.txt -r tests/functional/requirements.txt
PYTHONPATH=src python -m pytest -q
MYPYPATH=src python -m mypy --config-file ../../mypy.ini src
```

CI запускает Profile Compose на Python 3.10/3.11/3.12.
Живой полный стек проверяется
через регистрацию, создание профиля, роль сотрудника и существующий фильм
из Content: закладка → оценка → отзыв → чтение рейтинга и отзывов.
