# Notification Service

FastAPI-сервис уведомлений онлайн-кинотеатра. Принимает персональные заявки,
управляет версиями шаблонов и массовыми рассылками, обрабатывает события
регистрации и появления фильма, хранит результаты доставки. Основное
хранилище — PostgreSQL; транспорт заданий и результатов — Kafka.

Письма отправляет [Notification Worker](../notification_worker/README.md).
Notification API сохраняет заявку и outbox одной транзакцией и возвращает
`202`, не дожидаясь SMTP. Доступ к бизнес-методам разрешён активному
суперпользователю через существующий Auth Service.

## Зависимости

Сервис входит в монорепозиторий и запускается общим Docker Compose.

| Компонент | Назначение |
|---|---|
| PostgreSQL | База `notifications`; отдельная база `deliveries` для воркера |
| Kafka | Передача заданий, результатов и событий кинотеатра |
| Auth Service | Проверка полномочий, данные получателей и снимки аудитории |
| PostgreSQL Auth и кинотеатра | Транзакционные события регистрации и добавления фильма |
| Notification Worker | Подстановка данных пользователя и отправка через SMTP |
| Mailpit | Локальный SMTP-сервер и просмотр писем на порту 8025 |
| Jaeger | Приём трассировок OpenTelemetry |
| Nginx | Внешний доступ к API при запуске всего монорепозитория |

## Возможности

- персональное уведомление с неизменяемым снимком шаблона;
- идемпотентность по инициатору и `Idempotency-Key`, включая конкурентные запросы;
- транзакционная публикация заданий через outbox;
- создание, чтение, версионирование и архивирование шаблонов;
- рассылка всем активным пользователям, в том числе с отложенным началом;
- сохранение прогресса рассылки и состава её аудитории в Auth;
- приветствие при регистрации и рассылка при добавлении фильма;
- получение результатов отправки и защита от устаревших событий;
- метрики Prometheus, JSON-логи, опциональные Sentry и OpenTelemetry;
- отдельные liveness/readiness и корректная остановка фоновых процессов.

Поддерживается канал `email`. WebSocket, SMS, push, сокращатель ссылок,
периодические рассылки и отдельная административная веб-панель не реализованы.

## Архитектура

| Каталог | Ответственность |
|---|---|
| `src/api` | HTTP-методы и проверка полномочий через Auth |
| `src/core` | Настройки, пул PostgreSQL, жизненный цикл, health и телеметрия |
| `src/models` | Контракты заявок, шаблонов, заданий и событий |
| `src/repositories/interfaces` | Интерфейс хранения персональных заявок |
| `src/repositories/postgres` | Транзакции, идемпотентность, версии и прогресс рассылок |
| `src/services` | Сервисный слой приёма заявок и правила шаблонизации |
| `src/messaging` | Outbox, обработчики Kafka, подготовка рассылок и relay источников |
| `alembic` | Версионированные миграции PostgreSQL |

Два приложения запускаются несколькими процессами:

| Контейнер | Команда | Назначение |
|---|---|---|
| `notification-service` | `uvicorn main:app --host 0.0.0.0 --port 8000` | HTTP API |
| `notification-outbox` | `python -m messaging.outbox` | Публикация заданий |
| `notification-results` | `python -m messaging.updates results` | Обновление статусов доставки |
| `notification-events` | `python -m messaging.updates events` | Обработка событий кинотеатра |
| `notification-campaigns` | `python -m messaging.campaigns` | Создание заданий по страницам аудитории |
| `auth-events-outbox` | `python -m messaging.source_relay` | Публикация outbox из БД Auth |
| `film-events-outbox` | `python -m messaging.source_relay` | Публикация outbox из БД кинотеатра |

`messaging.outbox` делегирует общий цикл модулю `messaging.relay`.
Процессы запускаются в отдельных контейнерах: каждый фоновый процесс использует
внутренний HTTP-порт 8000 для health/metrics. Несколько процессов используют
один код сервиса, но имеют независимый жизненный цикл.

## Хранилище и сообщения

| Таблица | Назначение |
|---|---|
| `notifications` | Заявка, ключ идемпотентности, статус и последний результат |
| `outbox` | Сообщения, которые нужно опубликовать в Kafka |
| `inbox` | Идентификаторы уже обработанных входящих событий |
| `templates` | Имена шаблонов и признак архивирования |
| `template_versions` | Неизменяемые снимки версий |
| `campaigns` | Снимок шаблона, время начала, курсор и прогресс рассылки |

| Топик | Данные | Получатель |
|---|---|---|
| `notification-delivery-v1` | Задания с UUID пользователя и снимком шаблона | Worker |
| `notification-results-v1` | Исход попытки: `retry`, `sent`, `failed` | Notification API |
| `cinema-events-v1` | `user.registered` и `film.created` | Notification API |
| `notification-delivery-v1-dlq` | Некорректные сообщения и коллизии заданий | Ручной разбор |
| `notification-failed-v1` | Задания с окончательной ошибкой доставки | Ручной разбор |

Контракт задания содержит `schema_version=1`, `event_id`, `delivery_id`,
`notification_id`, `user_id`, `channel`, `template`, `context`, `trace_context`.
Email и ФИО worker получает непосредственно из Auth перед отправкой.
Копии контракта в двух приложениях необходимо менять согласованно.

## Конфигурация

Настройки читаются из окружения и `.env`. Пример локальной конфигурации —
`.env.example`. Если `.env` ещё не создан, выполните из корня монорепозитория:

```bash
for service in notification_service notification_worker; do
  if [ ! -f "services/$service/.env" ]; then
    cp "services/$service/.env.example" "services/$service/.env"
  fi
done
```

Auth также использует собственный `.env`. Пароли баз должны соответствовать
`infrastructure/postgres/notifications/init.sql`, а сервисные ключи — Auth.
Пример рассчитан на локальный стенд; для другого окружения задайте свои секреты.

| Переменная | Значение / назначение |
|---|---|
| `DATABASE_URL` | `postgresql+asyncpg://notification:notification@notification-postgres/notifications` |
| `KAFKA_BOOTSTRAP_SERVERS` | Три внутренних адреса брокеров из `.env` |
| `JOBS_TOPIC`, `RESULTS_TOPIC`, `EVENTS_TOPIC` | Топики заданий, результатов и событий |
| `DLQ_TOPIC`, `FAILED_TOPIC` | Топики ошибок контракта и окончательных ошибок доставки |
| `AUTH_BASE_URL` | `http://auth-service:8000/api/v1/`, с завершающим `/` |
| `INTERNAL_TOKEN` | `notification-api-local-test` |
| `AUDIENCE_PAGE_SIZE` | 100; допустимо от 1 до 500 |
| `POLL_SECONDS` | Пауза пустого цикла, по умолчанию 1 секунда |
| `KAFKA_TIMEOUT_SECONDS` | Таймаут Kafka, по умолчанию 20 секунд |
| `HEALTH_STALE_SECONDS` | Допустимый возраст heartbeat, по умолчанию 90 секунд |
| `SENTRY_DSN` | Пустое значение отключает Sentry |
| `OTEL_ENDPOINT` | `http://jaeger:4317`; пустое значение отключает экспорт |
| `SERVICE_NAME` | Имя процесса в ресурсах OpenTelemetry |

Ключ `INTERNAL_TOKEN` должен совпадать с `NOTIFICATION_API_TOKEN` в Auth.
Ключ worker — `notification-worker-local-test` — должен совпадать с
`NOTIFICATION_WORKER_TOKEN` в Auth. Доступ к бизнес-API использует пользовательский
Bearer-токен, а не один из этих двух сервисных ключей.

`CONSUMER_GROUP` используется общим Kafka-адаптером. Обработчики результатов и
событий явно выбирают отдельные группы `notifications-results-v1` и
`notifications-events-v1`, чтобы независимо читать свои топики.

`source_relay` получает `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`,
`POSTGRES_USER`, `POSTGRES_PASSWORD` из окружения своего контейнера. Для Auth и
кинотеатра эти параметры должны указывать на соответствующую исходную базу.

## Запуск и миграции

Из корня монорепозитория запустите уведомления и их зависимости:

```bash
docker compose config --quiet
docker compose up -d --build \
  notification-service notification-outbox \
  notification-worker notification-sender notification-results-outbox \
  notification-results notification-events notification-campaigns \
  auth-events-outbox film-events-outbox mailpit
docker compose ps -a
```

Compose запускает PostgreSQL, Auth, Redis, три брокера Kafka и Jaeger, применяет
миграции и создаёт топики. `kafka-volume-init` перед запуском брокеров назначает
каталогам volumes владельца `1000:1000`. Ручной `chown` не требуется.
Контейнеры миграций, `kafka-volume-init` и `kafka-init` завершаются с кодом 0;
остальные процессы продолжают работать.

В этом режиме Nginx не запускается, порты API доступны только внутри Docker.
Ручные проверки ниже выполняют HTTP-запросы из контейнера Auth. Mailpit доступен
в браузере по адресу <http://localhost:8025>.

Для запуска всего монорепозитория, включая Nginx:

```bash
docker compose up -d --build
```

Внешний адрес API в полном режиме — `http://localhost:8000`.
Swagger — `http://localhost:8000/notifications/docs`.

Создайте суперпользователя из настроек Auth:

```bash
docker compose exec auth-service python -m commands.create_superuser
```

При отдельном применении миграций:

```bash
docker compose run --rm notification-migrate
docker compose run --rm delivery-migrate
docker compose run --rm auth-notification-migrate
docker compose run --rm film-notification-migrate
```

Миграции приложений выполняются последовательно `0001` → `0002` → `0003`.
Миграция `0002` не поддерживает destructive downgrade: историю доставки
не следует удалять ради отката приложения. Не используйте `down -v` для обновления.
Перед обновлением существующей установки остановите процессы уведомлений,
сохраните резервные копии и примените миграции.

Для локального запуска API без Docker, из каталога сервиса:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
export PYTHONPATH="$PWD/src"
alembic upgrade head
uvicorn main:app --host 0.0.0.0 --port 8001
```

Заранее замените адреса PostgreSQL/Auth/Kafka/Jaeger на доступные с хоста.
Имена контейнеров из `.env` не разрешаются автоматически вне сети Docker.
API будет доступен на 8001, а не через Nginx. Фоновые процессы проще запускать
в отдельных контейнерах: несколько процессов на одном хосте конфликтуют за
служебный порт 8000 и общий файл heartbeat.

## API

Префикс: `/api/v1/notifications`. Каждый бизнес-метод требует заголовок
`Authorization: Bearer <access_token>` активного суперпользователя.

| Метод | Путь относительно префикса | Назначение |
|---|---|---|
| POST | пустой | Принять персональную заявку, `202` |
| GET | `/{notification_id}` | Прочитать статус доставки |
| POST | `/templates` | Создать шаблон, `201` |
| GET | `/templates?limit=100&offset=0` | Получить список, включая архивные |
| GET | `/templates/{id}?version=1` | Получить конкретную версию |
| PUT | `/templates/{id}` | Создать следующую версию |
| DELETE | `/templates/{id}` | Архивировать, `204` |
| POST | `/campaigns` | Принять массовую рассылку, `202` |
| GET | `/campaigns/{id}` | Прочитать прогресс и счётчики доставки |

POST заявки и POST кампании требуют `Idempotency-Key`: от 1 до 128 печатных
ASCII-символов без пробелов. Повтор того же тела возвращает прежний ID; другое
тело с тем же ключом возвращает `409`. Ключ ограничен инициатором и видом операции.

HTTP `202` возвращает `status=accepted`. Сохранённый статус доставки начинается с
`pending`, затем API получает `retry`, `sent` или `failed`. Статус `processing`
существует только в базе worker. `sent` означает принятие письма SMTP-сервером.

Swagger: `/notifications/docs`; ReDoc: `/notifications/redoc`;
OpenAPI: `/notifications/openapi.json`. В этой реализации Bearer-заголовок
читается напрямую, кнопка Authorize в Swagger не объявлена: для защищённых
методов используйте приведённые ниже команды HTTP-клиента.

## Шаблоны и рассылки

Допустимы простые подстановки `{{ variable }}`. Циклы, выражения и доступ к
атрибутам запрещены. Отсутствующая переменная приводит к ошибке доставки.
Для HTML значения экранируются. Имя и фамилия берутся из Auth; `context`
не может содержать ключи `email`, `first_name`, `last_name`.

Администратор отвечает за произвольный текст шаблона и остальные поля context:
не помещайте туда персональные данные. Запрет ключа `email` не анализирует
содержимое всех строк и не является фильтром персональных данных.

При прямом POST можно передать самодостаточный снимок шаблона: существование
его `template_id` в каталоге не проверяется. Для управляемого шаблона получите
версию через GET и передайте возвращённый объект в поле `template`.

Для одинакового текста всем получателям используйте шаблон без подстановок
пользовательских данных. Для персонализации добавьте `{{ first_name }}` и
`{{ last_name }}`: воркер заполнит их отдельно для каждого адресата.

Кампания выбирает версию при создании. Аудитория фиксируется в Auth при начале
разворачивания, затем читается по UUID. Курсор страницы и её задания сохраняются
одной транзакцией. Регистрации после снимка не меняют состав кампании. Деактивация
получателя до отправки приводит к окончательной ошибке, а не отправке письма.
Состояние `expanded` означает окончание подготовки заданий, не доставки писем.

Системные шаблоны `user.registered` и `film.created` создаются миграцией.
Их версии можно менять. Архивирование возвращает HTTP 409
`system_template_required`; ограничение PostgreSQL также запрещает отключение.
Миграция `0003` восстанавливает ранее архивированные системные шаблоны. Старые записи пользователей и
фильмов сами по себе не порождают события задним числом.

## Коды ошибок

| Код | Причина |
|---|---|
| 401 | Нет Bearer-токена или Auth отклонил его |
| 403 | Пользователь неактивен или не является суперпользователем |
| 404 | Уведомление, кампания или доступная версия шаблона не найдены |
| 409 | Конфликт ключа идемпотентности либо занятое имя шаблона |
| 422 | Некорректное тело, UUID, заголовок или синтаксис шаблона |
| 503 | Auth недоступен/вернул некорректный ответ; для `/ready` — недоступна БД |

Ожидаемая ошибка приложения содержит `detail`, например
`{"detail":"idempotency_key_conflict"}`. Ошибки валидации имеют стандартный
формат FastAPI со списком в `detail`. Общий `request_id` в JSON ошибки не добавлен.
При обращении через Nginx применяются ограничение тела и общий rate limit.

## Гарантии и ограничения

- Уведомление и outbox фиксируются одной транзакцией PostgreSQL.
- ACK Kafka предшествует отметке outbox: падение между ними допускает дубль.
- Consumer подтверждает offset после commit задания или успешной публикации DLQ.
- Уникальный delivery_id предотвращает повторное создание задания; другой payload
  с тем же ID считается коллизией и попадает в DLQ.
- Результат попытки и его outbox сохраняются вместе; старый владелец не может
  перезаписать результат новой аренды. API игнорирует устаревшие попытки.
- SMTP не предоставляет exactly-once. Письмо может повториться после таймаута
  с неизвестным исходом или падения сразу после принятия SMTP-сервером.
- Статус sent не подтверждает чтение письма или его попадание во входящие.
- Outbox/inbox, аудитории и история автоматически не очищаются. Срок хранения
  должен учитывать возможную повторную обработку старых сообщений.
- При retention.ms=-1 Kafka не удаляет сообщения по времени; нужен контроль диска.
- PostgreSQL в локальном стенде не имеет реплик. Сохранность томов и резервные
  копии остаются ответственностью инфраструктуры.

## Логи, метрики и диагностика

`/health` подтверждает работу процесса. `/ready` API проверяет основные таблицы
БД, но не гарантирует готовность всех внешних зависимостей. Readiness фоновых
процессов основан на свежести heartbeat после успешного цикла. Sender без заданий
может быть ready даже при недоступном SMTP: отправка проверяется на реальном задании.

JSON-логи доступны через docker compose logs; подключение к ELK выполняет общий
Filebeat. В JSON логов записываются level/logger/message; service.name для поиска
в Kibana зависит от обогащения событий общим стеком. Sentry и OTLP включаются
параметрами окружения. Docker healthcheck сам по себе не перезапускает живой
зависший процесс.

| Симптом | Что проверить |
|---|---|
| API отвечает 503 | Доступность Auth, затем PostgreSQL для readiness |
| Outbox не публикуется | Брокеры, топики/лидеры, published_at и логи relay |
| Задания есть, писем нет | Sender, его INTERNAL_TOKEN, SMTP и next_attempt_at |
| Письмо есть, API pending | Results outbox, results consumer, Kafka lag |
| Рассылка не продвигается | Время scheduled_at, токен API, внутренние методы аудитории |
| Событие блокирует consumer | Проверьте миграцию 0003 и наличие системных шаблонов |
